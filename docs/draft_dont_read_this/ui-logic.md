## UI 逻辑设计

### Table

1. 为了避免滚动来滚动去的问题，增加粘性表头、粘性左侧ID类column、粘性 Action Bar。
2. 使用 Dense 版本 Table，让信息密度更高。
3. TableHead 内，可以在每个表头 cell 旁边加一个更多按钮。在这里加选择列/隐藏列功能（第一个列不能隐藏），而不是放在表格外。
4. 表格存在 cell 大小不是由内容决定的问题（有些单元格真的太大了）。

### Action Bar

对于一个对象，什么需要放入操作一栏中： Imperative 的操作。例如，删除、冲 credit 不是一个配置过程，而是一个命令过程，所以它应该放入 Action Bar 而不是编辑界面。
以实际场景为例，人员与权限 tab 需要操作的则是：编辑个人信息、配置可用功能、分配 AI 配额、限制(Restrict)、注销帐号、删除帐号及其关联数据。

同样地，批量 Action Bar 直接 mirror 这一设计。只不过，对于编辑个人信息这种仅限单个条目的东西，不应该放入批量处理的范畴。

### 批量应用

关于多选框的三态逻辑，只需要介绍这么多，其他地方保持简洁，就不要加其他关于三态的帮助文本了。

```
勾选表示全部选择，半选表示存在不一致的选择，不选表示全部不选择。不变动的字段不会应用。
```

其他地方，也需要批量处理、应用的逻辑。例如，需要支持批量配置可用功能、批量分配 AI 配额、批量限制、批量删除或注销。组件应复用对单个用户进行操作的组件。这些组件需要支持增量处理；例如，开关型的就用三态处理；credit top-up 在单人操作时，显示所拥有的 credit 数量，批量就不能显示了。

为所有有 Table 的地方都添加这个逻辑。特别提醒一下你，群组的多选逻辑，需要重新设置它的 Action Bar，而不是什么都堆到编辑菜单里，拆分思路与人员那个例子相似。客户端准入也是一个道理。

### 帮助文本

需要增加更多内容，帮助管理员理解流程。如客户端准入 Tab 内需要讲清楚整个白名单机制、持久化机制、标识方式一起是怎么工作的，让管理员更好理解 Authentication Flow。其他面板需要相应地添加相应的说明。用 Help IconButton 收起来。

- 为了表达设计语义，我提供的都是简化示例，不要照着我随便编出来的东西来。
- 尽量不要参考现有的实现，它们都是 poorly implemented 的。我正是希望你能推翻这些糟糕的设计与代码。
- 允许你自由设计，你需要细致评估以上方案，提出你的深刻洞见。
- 改动不限制 scope，客户端与服务端一起改。
- 我希望得出一套干净的设计，把能改的地方都改好，避免反复返工，减少未来的困扰。
